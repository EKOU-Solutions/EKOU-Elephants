# Cómo trabajamos el diseño

**Regla global del proyecto** (`AGENTS.md`, la leen Claude, Codex y Antigravity): todo cambio visual o de experiencia pasa por uno de los flujos de diseño. No hay excepción para cambios pequeños. Si alguien pide un cambio sin usar un comando, el agente carga `elephant-designer` igual y sigue el flujo que corresponda.

## Qué comando usa cada cambio

| Pedido | Comando | Qué pasa |
| --- | --- | --- |
| Ajuste puntual que **mantiene la dirección** (un texto, un espaciado, un bug visual, un contraste) | `/ajuste` | Se revisa contra los tokens y el catálogo, se corrige, se actualiza la historia y se valida. |
| **Pantalla o página** para desarrollo (mapa, contrato, búsqueda…) | `/crear-pantalla` | Parte del contrato de nuestra API, explora los datos, propone bocetos con uno recomendado, define la especificación, construye la pantalla en Storybook, valida y entrega. |
| **Componente nuevo** | `/crear-componente` | Se piensa, se muestran variantes con una recomendada, se implementa, se revisa y queda con su commit. |
| **Revisar** algo ya construido (página, componente, commit, rama, cambios sin confirmar) | `/revisar-implementacion` | Revisión de experiencia y de calidad técnica; devuelve hallazgos y no cambia nada. |
| Juzgar todo el sistema, cambiar la dirección (paleta, tipografía) o actualizar el brief | `/elephant-designer` | Auditoría, ronda o descubrimiento. |
| No sé cuál | `/elephant-designer` | Clasifica el pedido y elige el flujo. |

Si un comando recibe un pedido que no es suyo, redirige al correcto. Ningún flujo publica ni marca algo como aceptado sin la instrucción de una persona del equipo; el único commit automático es el del componente al final de `/crear-componente`, después de la aprobación.

El paso a paso de cada comando está en `docs/design/comandos.md` y en la página **Cómo usar la skill**.

## Dónde vive un componente

Cada componente tiene su carpeta, con el componente y su historia al lado. Hay dos lugares, según quién lo usa. **Storybook refleja el módulo:** la pantalla y los componentes que arma quedan juntos en `Módulos/<Módulo>/`, igual que en `src/modules/<módulo>/ui/`.

| Tipo | Carpeta | Título en Storybook | Ejemplos |
| --- | --- | --- | --- |
| **UI**: puro y transversal; no conoce ninguna página ni pide datos | `src/components/ui/<Component>/` | `Componentes/UI/<Component>` | `Button`, `Alert`, `Input`, `Select`, `RiskTag`, `Counter` |
| **De módulo** (organismo): lo arma una página con los componentes UI; incluye los grandes (paneles, secciones, el mapa) | `src/modules/<módulo>/ui/<Component>/` | `Módulos/<Módulo>/<Component>` | `src/modules/mapa/ui/TerritoryPanel/` → `Módulos/Mapa/TerritoryPanel` |
| **Pantalla**: la página completa, armada con los anteriores. Es la maqueta que se aprueba y la que usa la aplicación | `src/modules/<módulo>/ui/<Page>Page/` | `Módulos/<Módulo>/<Page>Page` | `src/modules/mapa/ui/MapPage/` → `Módulos/Mapa/MapPage` |

```text
src/components/ui/RiskTag/
  RiskTag.tsx
  RiskTag.module.css
  RiskTag.stories.tsx
src/modules/mapa/ui/TerritoryPanel/
  TerritoryPanel.tsx
  TerritoryPanel.module.css
  TerritoryPanel.stories.tsx
```

Cada componente React trae **sus propios estilos** en `Component.module.css` (CSS Modules) junto al componente. No hay hojas de estilo compartidas entre componentes: lo único global son los tokens `--el-*`, la fuente y la base del documento (`src/styles/global.css`). Si un componente necesita el aspecto de otro, lo usa (composición); no copia ni comparte sus clases.

Un componente de página que otra página necesita se mueve a `src/components/ui/` solo si queda puro: recibe todo por props y no sabe de qué página viene.

## Cómo entra un componente a Storybook

1. Nace con `/crear-componente` (solo, o dentro de `/crear-pantalla`) y se aprueba.
2. Se implementa como componente React en su carpeta (ver la tabla de arriba), con **sus propios estilos** en `ComponentName.module.css` y usando solo tokens `--el-*`.
3. Se escribe su historia **al lado** del componente: `ComponentName.stories.tsx`, con `tags: ['autodocs']`. El código va en inglés (nombre del componente, props, variables y archivos); lo que lee una persona va en español: el título (`Componentes/UI/…` o `Módulos/<Módulo>/…`), el `name` de cada historia, la descripción de las props y los textos de la interfaz. Lleva una historia por estado: normal, vacío o «Sin datos», error, carga, y el caso de 320 px si aplica.
4. Se documenta en lenguaje claro: para qué sirve, cuándo usarlo, qué evitar y la accesibilidad.
5. Se actualiza `components.json` y, si existía, se retira la historia de especificación de `.storybook/catalog/`.
6. Se valida con `npm run design:check -- --filter <componente o módulo>`: render, accesibilidad (axe) y desplazamiento horizontal de cada historia a 320, 390, 768 y 1280 px, en claro y oscuro. Las capturas quedan en `.design-check/screenshots/`.

## Plantilla de historia

```tsx
import type { Meta, StoryObj } from '@storybook/react-vite';
import { RiskTag } from './RiskTag';

const meta = {
  title: 'Componentes/UI/RiskTag',
  component: RiskTag,
  tags: ['autodocs'],
  parameters: {
    docs: { description: { component: 'Para qué sirve, cuándo usarla y qué evitar.' } },
  },
} satisfies Meta<typeof RiskTag>;

export default meta;
type Story = StoryObj<typeof meta>;

export const High: Story = { name: 'Alto', args: { level: 'high' } };
export const Unknown: Story = { name: 'Sin datos', args: { level: 'unknown' } };
```

## Dónde vive cada cosa

| Qué | Dónde |
| --- | --- |
| Configuración de Storybook | `.storybook/main.ts`, `.storybook/preview.tsx` |
| Lineamientos (estas páginas) | `.storybook/docs/*.mdx` |
| Especificación de los candidatos (aún no son React) | `.storybook/catalog/candidates/` |
| Componentes UI transversales | `src/components/ui/<Component>/` |
| Componentes y pantallas de cada página | `src/modules/<módulo>/ui/<Component>/` |
| Tokens y catálogo (fuente de verdad) | `docs/design/guide/` |
| Flujo de la skill | `.claude/skills/elephant-designer/` (enlazada para Codex y Antigravity en `.agents/skills/`) |
| Historial de rondas | `docs/design/rounds/` |
